# Read the engine, not the screen

*Research for issues 238 and 239, November 2026. Source notes are in [game-state-perception/](game-state-perception/). Nothing here was run live; the summary table at the end marks what still needs a live check.*

The civ_6_ai bot is not missing a vision stack. It is missing a handful of **engine calls that the game's own UI already makes**, plus three or four well-established game-AI techniques for turning those reads into decisions. The biggest single correction is about loyalty. PR 240 concluded that the settler loyalty numbers could not be read through MCP. That was very likely wrong. The shipped UI file `SettlerInfluenceIconManager.lua` gets every number it draws from one call, **`Map.GetContinentPlotsLoyalty()`**. That call is UI-context only, and the bot already runs Lua in the InGame context. Three other Civ VI automation projects and an accessibility mod read it this way today. This is **verified from the game files and other projects' code but not yet run live in this repo**. For the threat map (issue 238 / PR 241), the design already matches the core of Civ V's community danger-map code. The upgrades with the best evidence are these: measure danger as **expected damage from the Civ VI combat formula** instead of summed strength; split "can hit us this turn" from "can arrive in N turns"; give remembered units **weights that decay per unit class**; replace the generic fog penalty with a **barbarian-camp spawn-eligibility mask** built from the game's own parameters; and test the game's **combat preview** (`CombatManager.SimulateAttackVersus`) as a ground truth. Pixel vision is not worth it for any state the API exposes. Every benchmark that compares the two finds text equal to or better than images for LLM agents, and the screen route costs far more in tokens and time. Vision earns a narrow place in detecting stuck popups and in offline consistency checks.

## Loyalty numbers come from one engine call PR 240 missed

The settler loyalty preview is not computed in UI Lua. The engine computes it, and the Gathering Storm UI script `DLC/Expansion2/UI/Additions/SettlerInfluenceIconManager.lua` (lines 95-126) reads it with `local plots = Map.GetContinentPlotsLoyalty()`, loops `for plotID, loyaltyVal in pairs(plots)` and draws each value as the flag-and-number icon ([UI file mirror](https://github.com/civfanatics/Civ6-UIFiles-Restructured/blob/master/DLC/Expansion2/UI/Additions/SettlerInfluenceIconManager.lua)). The English tooltip defines the number: "The influence of nearby cities would apply {1_LoyaltyPerTurnAmount} Loyalty per turn to a new city settled here" (local install, `Expansion1_InGameText.xml` lines 565-566). A community API knowledge base lists the function as **UI: true, Script: false**, with no arguments ([Sukritact KB](https://github.com/Sukritact/Civilization-VI-Modding-Knowledge-Base/blob/main/Objects/Map/Map.GetContinentPlotsLoyalty.md)). This explains why a GameCore search would come up empty. The PR 240 search also looked for "loyalty" and "identity" file names and missed a file named "SettlerInfluence".

Other projects already read it the way this bot would. **CIVVIS**, another Civ VI AI, exports the table "for revealed plots only", queries "only for the local player while an owned Settler exists", and changes no unit selection or lens state. Over 100 turns it logged 163 non-empty tables with no malformed values. Values appeared from turn 39 "without selecting a unit or changing a lens" ([CIVVIS eval](https://github.com/MartinHalvorson/CIVVIS/blob/HEAD/docs/eval/2026-10-15-native-settlement-loyalty-warnings.md)). CIVVIS also has the best evidence that the number means something. It settled a plot showing **-20**, the city's real first-turn rate was -20, a governor brought it to -12, and the city revolted eight turns later. Its fixed planner then rejected such sites ([CIVVIS forecast eval](https://github.com/MartinHalvorson/CIVVIS/blob/HEAD/docs/eval/2026-10-15-native-settlement-pressure-forecast.md)). The civ6-mcp fork **auto-civ6** wraps the same call in `pcall` with the comment "Missing entry is not evidence of zero pressure" ([auto-civ6 map.py](https://github.com/Harryleft/auto-civ6/blob/HEAD/src/civ_mcp/lua/map.py)). **XenoAmess/civ6_dev** reads it only for revealed, visible, unowned-or-ours plots ([settlement_warning_info.lua](https://github.com/XenoAmess/civ6_dev/blob/HEAD/tools/lua/settlement_warning_info.lua)). The **Civ VI Accessibility Integration** screen-reader mod speaks the value aloud as "+N/-N" ([interfaceInfoHelpers_CAI.lua](https://github.com/flat-arther/Civ-VI-Accessibility-Integration/blob/HEAD/src/UI/inGame/interfaceInfoHelpers_CAI.lua)). That mod is a useful fairness precedent: it is exactly "the human-visible preview delivered as text".

No mod or bridge is needed in this repo. The installed civ6-mcp already finds the `ingame_index` Lua state, and the bot already sends bespoke snippets there, for example `game.execute_lua(CITY_TILES_LUA, "ingame")` in `src/civ6_ai/city_tiles.py`. The recommended read is one short InGame snippet per turn, sent during the bot's own turn and never while AI civs are moving (civ6-mcp's `end_turn.py` warns about this). It is gated on "we own a settler or one is in production", filtered by `PlayersVisibility[me]:IsRevealed`, and returns `index,value` lines. Feed the value into `policies/settling.py` as the nearby-city pressure term. Keep modelling governor (+8), amenities and policies on top, since the preview leaves those out ([CivFanatics loyalty guide](https://forums.civfanatics.com/resources/civ-vi-loyalty-guide.27114)). Keep the current formula as a fallback, and log both numbers so the formula can be calibrated with no screenshots.

Four things still need a live check before this ships. First, **whether the call works at all from this repo's tuner connection.** Second, **what "Continent" covers**: CIVVIS tested only on a one-continent Tiny Pangaea map. Third, **whether a missing plot means zero or unknown**: treat it as unknown. Fourth, **whether values are clamped**: issue 239's screenshot shows -22, but the community formula clamps at ±20.

Three fairness points apply. Drop plots the player has never revealed, because a value there could reveal a hidden foreign city. Accept that a value on a revealed plot may include pressure from an unseen foreign city. The human sees the same number on that tile, so register the read in `state/fog.py` as FLAGGED, and never back-solve city positions from the values. Read only while a settler exists or is planned, since that is when a human sees the icons.

## The same pattern opens a dozen other "UI-only" reads

Loyalty is one case of a general rule. Previews, tooltips and overlays come from engine functions exposed only to UI Lua. The way to find them is to **grep the shipped UI Lua for the tooltip's LOC tag or the lens layer name, open the drawing context (`*IconManager.lua`, `*Lens*.lua`, panels) and read the engine call it makes**. The game install on this machine was searched this way. The table below lists the highest-value finds with their fog ratings. "Verified" means the call was seen in the shipped UI or another project's code. None has been run live in this repo yet, and the exact Lua context of each is undocumented, so a one-line `print(type(X))` probe in the InGame state should come before building on any of them ([CivFanatics: context availability is "hit or miss"](https://forums.civfanatics.com/threads/lua-objects.601146/page-5)).

| Human tool | Engine call (from shipped UI Lua) | Use for the bot | Fog rating |
|---|---|---|---|
| Combat preview on hover | `CombatManager.SimulateAttackVersus(attackerID, defenderID, type)`, `SimulateAttackInto(unit, type, x, y)` (`UnitPanel.lua` 3319-3352) | Exact expected damage with all modifiers, for force sizing and threat checks | Legal only against a **visible** target, and only when `UI.IsGameCoreBusy()` is false |
| Selected-unit move and attack overlay | `UnitManager.GetReachableMovement`, `GetReachableTargets`, `GetReachableZonesOfControl(u, true)` (`SelectedUnit.lua` 47-74) | Own-unit reach without reimplementing movement and ZOC | Legal for own units. **Unknown** for enemy units, so treat as a leak until tested |
| Path preview with turn numbers | `UnitManager.GetMoveToPathEx(unit, plot)` (`WorldInput.lua` 961-975) | Turn-quantized paths | Own units only. The repo already found the related `GetMoveToPath` answering for unrevealed tiles, so the same guard applies |
| District adjacency preview | `plot:GetAdjacencyYield(player, cityID, district, yield)`, `CanHaveDistrict` (`AdjacencyBonusSupport.lua` 188-317) | Replaces hand-coded adjacency rules | Legal (own cities) |
| Loyalty lens and city panel | `city:GetCulturalIdentity()` then `GetCityIdentityPressures`, `GetIdentitySourcesDetailedBreakdown`, `GetTurnsToConversion` | Own-city revolt risk. A foreign city is legal only if visible | Legal for own cities. Visibility-gate foreign ones |
| Settler flood and volcano warnings | `SettlerWarningIconManager` context, `RiverManager.CanBeFlooded` | Settle-site hazards | Legal |
| Power lens | `pCity:GetPower():GetPlotsCoveredByRegionalPower()` etc. | Power planning | Legal (own cities) |
| Notifications | `NotificationTypes.BARBARIANS_SIGHTED`, `NEW_BARBARIAN_CAMP`, `CITY_RANGE_ATTACK` | A free "something appeared" event feed for the threat map | Legal. Payload coordinates not checked |

All of these come from local game files under `Base/Assets/UI` and `DLC/Expansion2/UI`, and community mods confirm the pattern. **More Lenses'** barbarian lens loops all plots, checks `IsRevealed` and tests for `IMPROVEMENT_BARBARIAN_CAMP`, which is exactly what the threat map's camp read does ([ModLens_Barbarian.lua](https://raw.githubusercontent.com/astog/MoreLenses/master/Lenses/Barbarian/ModLens_Barbarian.lua)). CQUI and More Lenses add useful derived views, such as city overlap at range 6/9, unimproved resources and goody huts. They add no new data ([MoreLenses README](https://github.com/astog/MoreLenses)).

Two engine reads must stay **excluded**. `player:GetInfluenceMap()` is the game AI's own danger map. Only the FireTuner AI debug panel uses it (`TunerAiPanel.lua` lines 1-27), and it is almost certainly computed with full knowledge. `GetDiplomaticAI():GetThreatFrom/GetTrustFrom` is AI opinion that no shipping screen shows. One more warning applies to the existing threat map. Plot getters such as `GetImprovementType()` return **live** values even when the caller tested only `IsRevealed`, so on a fogged tile they can report that a camp is gone when the player's map still draws it. More Lenses has the same leak. `docs/threat-map.md` says camps are dropped only when a *visible* tile shows no camp, and keeps the map's remembered camp on fogged tiles via `build_tile` and `state/fog.py`. Someone should **confirm that the camp read uses the remembered fog image, not the live improvement getter**, on any fogged tile.

## Threat map: right skeleton, wrong currency

What PR 241 has built is close to the most inspectable shipping reference, Civ V's `CvDangerPlots` in the open-source Community Patch (Vox Populi). That code also rebuilds danger from hostile units' reach, adds a fog penalty (1 per hidden plot within 2 of a unit or 3 of a city), remembers vanished units for one turn, and keeps revealed barbarian camps ([CvDangerPlots.cpp](https://raw.githubusercontent.com/LoneGazebo/Community-Patch-DLL/master/CvGameCoreDLL_Expansion2/CvDangerPlots.cpp)). The project's legal-read stance is actually stricter than that code: a 2014 Civ V changelog admits major civs "see" barbarians on revealed tiles as a knowledge cheat ([Steam changelog](https://steamcommunity.com/sharedfiles/filedetails/changelog/312060464?p=2)). Freeciv's classic AI has the same shape. Its `assess_danger()` uses a reverse path map from each city, divides danger by move time, and keeps two counts: `grave_danger` (units that can attack next turn) and `urgency` (units within three turns, plus 10 × grave danger) ([daimilitary.c](https://github.com/freeciv/freeciv/blob/main/ai/default/daimilitary.c)). The skeleton is sound. The gaps are in the unit of measure and in how memory and fog behave.

**1. Measure threat and cover as expected damage, not summed strength.** The local `GlobalParameters.xml` gives `COMBAT_BASE_DAMAGE` = 24, `COMBAT_MAX_EXTRA_DAMAGE` = 12, `COMBAT_POWER_SCALING` = 0.04 and 100 HP. That matches the community fit of damage ≈ (24 + U{0..12}) × e^(0.04 × strength difference) ([CivFanatics formula thread](https://forums.civfanatics.com/threads/hans-lemurson-figures-out-the-combat-formula.606147/)). Because damage is exponential in the difference, **two warriors are not worth one strength-40 unit**. The current "cover from real combat strength, no cap" layer overstates swarms of weak units and understates one strong one. Vox Populi also expresses danger as simulated damage against a specific defender, with no random roll ([CvDangerPlots.cpp](https://raw.githubusercontent.com/LoneGazebo/Community-Patch-DLL/master/CvGameCoreDLL_Expansion2/CvDangerPlots.cpp)). Keep "one point = one barbarian warrior" for display, but have `net_value`, garrison sizing and retreat decisions compare **expected damage against HP**. Because the roll is a uniform 13-value integer, a sequence of attacks gives an exact distribution by convolution, which takes microseconds. The wounded penalty (`COMBAT_WOUNDED_DAMAGE_MULTIPLIER` = 10, read as roughly -1 strength per 10% HP lost) and barbarian +4 defence (`BARBARIAN_DEFENSE_ALL_UNITS`) are inferred from parameter names and community posts. **Check them against `CombatManager.SimulateAttackVersus` on visible pairs** and use the preview as the test oracle for the model.

**2. Split "this turn" from "within N turns".** Vox Populi's tactical danger uses only one-turn reach (move plus attack range). Freeciv keeps one-turn and three-turn counts apart. The turns-to-arrive field from stage 1b already supports both. Policies should read the turn-1 slice for safety and the multi-turn field for strategy, and expose two counts per city, "can hit next turn" and "within 3", next to the summed heat. Dave Mark's influence-map chapter recommends a flat-then-drop (exponent 4) falloff for threat rather than linear ([Mark, Game AI Pro 2 ch. 30](http://www.gameaipro.com/GameAIPro2/GameAIPro2_Chapter30_Modular_Tactical_Influence_Maps.pdf)). In a turn-based game the equivalent is a **step on turns-to-arrive**, which carries more meaning than linear fade by distance. The same chapter notes that ranged units (archers, catapults, cities) project a **ring at firing range** from every reachable tile, not a blob centred on themselves.

**3. A civilian rule.** Vox Populi treats any tile a hostile melee unit can enter this turn as infinite danger to a civilian, because the unit would be captured. This is cheap to add and directly protects settlers and builders.

**4. Decaying memory per unit class, and drop a memory when its predicted tile is seen empty.** Weber, Mateas and Jhala's particle model for StarCraft keeps one "particle" per last-seen enemy, moves it, decays its weight linearly at a rate per class, and culls it when its predicted position is visible and empty. Their learned rates were 0.00 for buildings and workers and 0.04 per update for ground attackers. It beat plain last-seen memory (0.739 vs 0.669 accuracy) and raised win rate from 67% to 78% over 144 games ([Weber et al., AIIDE 2011](https://ojs.aaai.org/index.php/AIIDE/article/view/12424)). The project's `unit_memory_turns` hard cutoff is that paper's weaker "Default" model. The upgrade is a weight that falls each turn at a per-class rate: camps 0, slow units low, horsemen, scouts and ships high. A hex game also allows a better version than one moving particle. Spread each remembered unit over its **reachable set** (all tiles within k turns of movement, minus visible tiles), which takes one Dijkstra per source. The size of that set is a natural confidence measure. Learned "defoggers" are not worth it yet: the neural defogger gained about 5 win-rate points from 65,000 replays and "seems to hurt the existing Tactics module more than help it" ([Synnaeve et al. 2018](https://arxiv.org/abs/1812.00054)). The run logs in `runs/*_threatmap.jsonl` could later fit decay rates offline with Nelder-Mead, as Weber did.

**5. Replace the fog penalty with a camp spawn-eligibility mask.** The local game file gives `BARBARIAN_CAMP_MINIMUM_DISTANCE_CITY` = 4, `..._ANOTHER_CAMP` = 7 and `BARBARIAN_CAMP_MAX_PER_MAJOR_CIV` = 3, and a 2016 community reference reports the same values ([r/civ map settings reference](https://lr.eu.psf.lt/r/civ/comments/59lsbf/map_settings_reference_everything_ive_found)). Players widely report that camps spawn only in fog ([gamepressure guide](https://www.gamepressure.com/sidmeierscivilization6/barbarians/z49335)). A mask of fogged land at least 4 from any known city and 7 from any known camp turns "mild fog penalty" into "where can the next camp appear". It also ranks **fog-busting posts**: place a unit where it removes the most hazard-weighted eligible tiles. The mask uses only known cities, so it over-covers. That is conservative and leaks nothing. Two parts are community claims only: fog-only spawning, and the reported raid trigger, where a barbarian scout that sees a city and returns sets off a 3-6 unit raid ([CivFanatics: barbarian scouting](https://forums.civfanatics.com/threads/barbarian-scouting.652484/)). If the trigger is real, a **barbarian scout near a city is a leading indicator** and a high-value kill target.

**6. Derived layers and fast plumbing.** Once threat and cover are numpy arrays, the standard derived layers cost almost nothing: `control = cover − threat` (the front line lies where the sign flips), `tension = cover + threat`, and Mark's "interest template" multiply for choosing garrison and recon targets ([Mark, GAIP2 ch. 30](http://www.gameaipro.com/GameAIPro2/GameAIPro2_Chapter30_Modular_Tactical_Influence_Maps.pdf)). No fetched source names who first defined these formulas. A flee map for civilians and wounded units follows the RogueBasin Dijkstra-map recipe: scale the distance-to-threat field by about −1.2 and re-relax it ([RogueBasin](https://www.roguebasin.com/index.php/The_Incredible_Power_of_Dijkstra_Maps)). `scipy.sparse.csgraph.dijkstra(indices=sources, min_only=True, limit=horizon)` returns a multi-source distance field plus the nearest source per tile in one compiled call ([SciPy docs](https://docs.scipy.org/doc/scipy/reference/generated/scipy.sparse.csgraph.dijkstra.html)). Two pitfalls follow from inference. Civ movement cost is **asymmetric** (cost to enter the destination, plus a river-crossing cost), so the graph must be directed. Movement is also **turn-quantized**, so summed cost divided by moves underestimates turns for slow units in rough terrain. The handler's current 0.36 s per turn should drop to milliseconds with a cached adjacency, but that is not benchmarked.

**7. Scout for relevant staleness, not raw age.** The planned `oldest_knowledge` will send scouts to far, irrelevant corners. Bayesian search theory gives the exact update after "looked and saw nothing", p' = p(1−q)/(1−pq), and says to search where probability per unit of cost is highest ([Bayesian search theory](https://en.wikipedia.org/wiki/Bayesian_search_theory)). Score each recon target as hazard-weighted staleness near our cities, divided by turns to reach and multiplied by the scout's survival odds from the threat layer.

## Pixels pay only where the API is blind

Every comparison found points the same way. In BALROG (ICLR 2025), adding images cut GPT-4o's average progress from 32.34 to 22.56 and llama-3.2-11B's from 16.82 to 8.43. Claude 3.5 Sonnet rose only slightly, from 32.64 to 35.48 ([BALROG](https://arxiv.org/html/2411.13543v2)). In a grid-maze study, Gemini-2.5-Flash scored 80-86% with adjacency text and 16-34% with visual grids ([arXiv 2604.10690](https://arxiv.org/abs/2604.10690)). Anthropic's own docs say Claude's coordinates are "approximate" and its counts of many small objects may be inaccurate ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)). In a 2026 benchmark on a non-game task, a vision agent took 53 steps, about 1,003 s and about 551k tokens, while an API agent took 8 calls, 19.7 s and about 12.2k tokens ([Reflex](https://reflex.dev/blog/computer-use-is-45x-more-expensive-than-structured-apis/)). The newest Civ VI benchmark, **CivBench**, deliberately turns state into deterministic text and marks fog as `[fog]` rather than leaving it out. Its main failures were attention and follow-through, not perception. Its games cost **$31-229 each**, 30-200× this project's target ([CivBench](https://arxiv.org/html/2609.02459)). The bot's own founding bug, a camp "forgotten" for thirty turns, was a memory failure, and pixels would not have fixed it. Learned screen parsers do not fit the 10 s budget: OmniParser V2 takes 0.6-0.8 s per frame on an A100 or RTX 4090 ([Replicate](https://replicate.com/microsoft/omniparser-v2)).

Money is not the obstacle. A 1-MP image costs about $1.30 per thousand on Haiku 4.5 ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)), so one per turn for 330 turns is under $0.50. Accuracy and latency are the obstacles. Vision is worth it in three narrow places. The first is a **stuck-popup detector**: OpenCV template matching runs in roughly 10-30 ms on CPU ([BrainDrip](https://braindrip-web.vercel.app/courses/computer-vision-concepts/feature-extraction-and-classical-vision/template-matching)) and VideoGameBench shows perceptual hashing works for "is the screen in state X" ([VideoGameBench summary](https://www.emergentmind.com/papers/2505.18134)). Fire it only when the API says the turn should advance and it does not, so it names a cause instead of adding a timer. The second is **offline consistency checks**: Tesseract on a tight crop takes about 0.16 s ([imagetotable.ai](https://imagetotable.ai/blog/ocr-speed-vs-accuracy-tradeoff)) and can compare a few API values against the per-turn screenshot to catch bad reads. The third is an **experimental render-then-ask** for rare frontier-model calls. Send the existing `threat_map_view.py` image with Set-of-Mark-style tile IDs drawn on it, so the model answers with IDs instead of pixel positions ([Set-of-Mark](https://arxiv.org/abs/2310.11441)), and always send the same facts as text alongside it. SpatialEval found that adding an image to a full text description sometimes lowered accuracy ([SpatialEval](https://arxiv.org/html/2406.14852v2)), so measure before keeping it, and keep images away from the cheap tier.

For the routine LLM tier, the representation should follow CivBench and OpenAI Five: a short list of precomputed facts, one line per threat source, giving what it is, where, expected damage, turns to our nearest city, local cover and age. OpenAI Five likewise fed ~16,000 API values with a few derived features like "distance to me", and never used pixels ([Berner et al. 2019](https://arxiv.org/abs/1912.06680)). By inference, a 10-line summary is about 150-300 tokens. A multi-layer hex grid would run to thousands.

## Conclusion

The useful human-built tools turned out to be the game's own UI scripts, not computer-vision models. Each lens, tooltip and preview is a readable index to an engine call, and the right discovery method is to grep the shipped UI for the tooltip text, not to search for the concept's name. That one change in method found what PR 240 missed. It probably applies wherever the bot "cannot see" something a human can. The fairness work then moves from "can we read it" to "filter to what was revealed, and read it when a human would". The UI hides things through fog rendering, not by filtering data, so every such read needs its own visibility gate.

On the threat map, the gap between this project and established practice is now small and specific. The project's memory and fog handling are already stricter than shipping Civ V. The next step is quantitative, not structural: change the currency from strength to expected damage, change the clock from distance to turns, and let memory fade instead of expire. Once the combat preview is verified live, it gives the project something most game-AI teams lack: an exact oracle to test its own model against, at no cost.
